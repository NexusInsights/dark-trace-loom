The invitation function now accepts the optional, nonsecret `RESEND_FROM_EMAIL` setting. Set it to the bare address `noreply@tjk-security.com` for the currently verified Resend domain. The outgoing header becomes `TJK Security <noreply@tjk-security.com>`; the address is preserved exactly. Resend requires the sender's domain to be verified. [Resend sender reference](https://resend.com/docs/api-reference/emails/send-email)

When the setting is absent, the original `TJK Security <invites@tjksecurity.com>` sender remains. An empty, malformed, display-name, whitespace, control-character or multiple-address value fails with `invalid_sender_configuration` before an invitation is inserted or Resend is called. Set this variable on the owned backend, then include the revised function in the reviewed deployment bundle. The API key remains a separate private `RESEND_API_KEY` credential and must be entered through the backend's approved secrets interface.

Supabase Auth SMTP is separate from the invitation API configuration. The prepared Auth sender is `noreply@tjk-security.com`; the human is entering the existing provider credential privately, and the prepared form has not been saved by this subtask. Resend's SMTP connection uses `smtp.resend.com`, port `465`, and username `resend`; its password is the API key. Never put that password in this repository, a frontend variable, or deployment evidence. [Resend SMTP reference](https://resend.com/docs/send-with-smtp)

This change is implemented and covered by isolated handler tests. No secret was read, mail sent, settings saved, or deployment performed by the sender preparation. Live acceptance requires the sender setting, provider credential, deployment, and an explicitly authorized invitation followed by the provider receipt and delivery check. Unit responses are controlled fixtures and are not delivery evidence.
