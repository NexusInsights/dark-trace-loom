# Investigation platform research — 1 November 2026

This is a primary-source documentation review for the existing Osintshadow and Insight Nexus apps. No product account was created, gated product scraped, provider query executed, key requested, purchase made, or proprietary code copied. “Documented” below means a capability or interface is described by its owner; it does not mean this session exercised that vendor product or that the user's account has entitlement. The implementation recommendations are independent engineering judgments.

The highest-value scope is a common evidence and investigation layer around the apps' existing collectors. Preserve each observation, source, timestamp, permission and provider outcome; then support reviewable claims, graph exploration, controlled enrichment and portable exports. A large graph by itself does not establish that a relationship is true.

## Eight capabilities to implement, with acceptance criteria

### 1. Typed, source-linked observation and claim records — first priority

Build common `Case`, `Entity`, `Identifier`, `Observation`, `Claim`, `Relationship`, `Source`, `Artifact` and `Run` records. A claim should refer to observations rather than replacing their values. Keep source reliability, analyst confidence and any classifier probability as distinct fields. Two matching usernames are an investigative lead, not sufficient identity proof.

Acceptance: import a synthetic fixture containing two organizations, two same-name people, a public profile, an IP observation and conflicting employment assertions. Every displayed fact and graph edge opens its source URL/artifact, provider/run ID, original value, capture time and review state. Missing values remain unknown. Reimporting the same source item is idempotent; conflicting values survive independently. Case access is enforced by the existing app backend.

Evidence: Palantir documents objects/links/actions; OpenCTI explicitly separates source reliability from information confidence; i2 documents source reference fields. These support the pattern, not a requirement to adopt any proprietary implementation. [Ontology](https://www.palantir.com/docs/foundry/ontology), [reliability/confidence](https://docs.opencti.io/latest/usage/reliability-confidence/), [i2 source references](https://docs.i2group.com/analyze/4.4.6/implementing_source_references.html).

Confidence: high for the independent feature; initial scope should be the existing collectors plus uploaded evidence, not an assertion of universal identity resolution.

### 2. Reviewable, reversible identity resolution

Create candidate matches with an explanation: normalized identifier match, shared source identifier, name similarity or analyst assertion. Keep “candidate”, “accepted”, “rejected” and “withdrawn” decisions. Preserve the original source records and allow an accepted resolution to be undone. Avoid globally merging people just because names or aliases match.

Acceptance: the same-name fixture never auto-merges; an exact same-provider record ID deduplicates; a reviewer can compare evidence, accept a candidate, see the actor/time/reason and undo it without losing observations. Concurrent edits produce a conflict response. Rejected candidates do not reappear unchanged after every import.

Evidence: i2 explicitly offers IGNORE, UNITE and MERGE handling, and preserves multiple provenance inputs in merged records. Gotham exposes resolve/unresolve operations. OpenCTI warns manual merges are irreversible, making reversible app-level decisions a useful improvement rather than something to copy blindly. [i2 matches](https://docs.i2group.com/analyze/4.4.7/detecting-matches-results.html), [i2 provenance during merge](https://docs.i2group.com/analyze/4.4.3/c_merge.html), [Gotham REST index](https://www.palantir.com/docs/docs/gotham/api), [OpenCTI deduplication specification](https://github.com/OpenCTI-Platform/connectors/blob/master/docs/02-external-import-specifications.md).

Confidence: high for a bounded review workflow; no documented general-purpose method guarantees correct identity attribution.

### 3. Graph and timeline that preserve evidence semantics

Build an interactive graph of selected case entities with typed, directed relationships, source/review filters, bounded expansion and a companion event timeline. Distinguish an observed link from an inferred or analyst-created link. Store event time separately from capture/ingest time. Do not treat centrality as guilt, influence or factual confidence.

Acceptance: synthetic graph filters/hop expansion return the same counts as the underlying records; edge selection shows supporting observations; reversing a directed edge changes its meaning; removing a source filter removes only its supported observations. Timeline handles unknown dates and time zones explicitly. A 500-node test remains usable on desktop, with a list/detail alternative on mobile and keyboard-accessible selection.

Evidence: OpenCTI models relationships as objects with their own properties. FtM documents that property-to-node conversion is a choice; its graph-export guidance warns that folder/page artifacts can bias path/density analysis. Maltego's transform guidance emphasizes small typed outputs for useful link analysis. [OpenCTI model](https://docs.opencti.io/latest/usage/data-model/), [FtM graph exports](https://docs.aleph.occrp.org/developers/followthemoney/ftm/), [Maltego transform modeling](https://docs.maltego.com/support/solutions/articles/15000034010-what-is-a-transform-).

Confidence: high for exploration; analytical conclusions still require review.

### 4. Provider registry, run lineage and audit

Wrap existing providers in a common run record containing action, normalized input digest, actor/case, connector version, start/end, state, attempt count, safe error code, returned-count/completeness, entitlement-check state and source references. Separate “configured”, “entitlement verified”, “last request succeeded” and “coverage unknown”. Apply allowlists, timeout/cancellation, concurrency and spend controls before a job starts. Keep secrets exclusively in existing server interfaces.

Acceptance: unauthorized/invalid input creates no provider request or paid work; replayed idempotency keys do not duplicate jobs; 401/402/403/429/timeout/partial/empty results remain distinct; cancellation does not become success; provider health does not imply search completeness. Audit captures who exported, reviewed, merged or ran a provider and includes an integrity checkpoint without exposing raw keys or unrestricted personal inputs.

Evidence: Foundry documents user/resource/action audit records and build/data lineage. OpenCTI uses separate tokens/users for connectors. SL API documents allowance metadata and asynchronous tasks, illustrating why adapters must model work beyond a single fetch. [Foundry audit](https://www.palantir.com/docs/foundry/security/audit-logs-overview), [lineage](https://www.palantir.com/docs/foundry/data-lineage/navigation), [OpenCTI connectors](https://docs.opencti.io/latest/deployment/connectors/), [SL API task/cost controls](https://sl-api-docs.readthedocs.io/en/latest/usage-of-parameters.html).

Confidence: high; reuse the apps' existing auth, provider allowance gates and remote browser boundary.

### 5. Evidence bundles plus an actual Hunchly-compatible ingestion seam

Implement a versioned manifest for uploaded raw artifacts and permitted captures: SHA-256 of the exact bytes, URL, capture method/time, receipt time, actor, content type, size and any supplied signature. Add a bounded Hunchly JSON import and authenticated HTTPS forwarding receiver with deduplication. Treat HTML/JavaScript as inert untrusted content. Importing metadata without the original MHTML must not show “file hash verified”.

Acceptance: independently recomputing an exported file's hash matches the manifest; altering one byte fails verification; originals remain unchanged after annotations. Hunchly's documented sample fields map correctly, duplicate page IDs in different case/device namespaces do not collide, oversized/malformed requests fail safely, untrusted page content cannot execute, and the receiver rejects an unauthenticated request before parsing/storing content. A real installed/licensed Hunchly forwarding test is a separate integration postcondition, not established by fixture tests.

Evidence: Hunchly forwards capture JSON including URL/time and the local MHTML hash; it retains local evidence. Its evidence guide explicitly says hashes alone cannot prove the content was not changed before submission, and documents GPG signing/export. [Forwarding schema](https://support.hunch.ly/article/67-2-hunchly-data-forwarding), [hash limitations](https://support.hunch.ly/article/52-2-content-photo-and-attachment-hashing), [signing](https://support.hunch.ly/article/53-3-gpg-signing), [exports](https://support.hunch.ly/article/30-11-exporting-cases).

Confidence: high for a documented file/HTTP adapter; no claim of court admissibility or remote-source authenticity.

### 6. Draft findings, evidence review and evaluated AI assistance

Use an explicit draft/review/approved lifecycle for extracted assertions and reports. AI assistance, if the existing approved model route supports it, proposes structured claims with citations and abstains where evidence is missing. It must not silently promote predictions into observations. Record model/prompt/config versions and human decisions; keep deterministic report generation usable without an AI call.

Acceptance: a reviewer sees a field-level diff and cited evidence, approves/rejects with a reason, and cannot approve another tenant's draft. Approved reports preserve their evidence snapshot. An unsupported assertion fails citation validation. A fixture suite includes contradiction, identical names, missing dates, malicious instructions inside documents, stale facts and empty results; compare outputs/metrics across versions. AI execution does not gain new provider permissions.

Evidence: OpenCTI drafts isolate edits and provide side-by-side review before approval. Palantir action criteria check user/context/parameters, while AIP Evals compares explicit inputs/expected outputs and per-case metrics. [OpenCTI drafts](https://docs.opencti.io/latest/usage/draftWorkspaces/), [action criteria](https://www.palantir.com/docs/foundry/action-types/submission-criteria), [AIP Evals](https://www.palantir.com/docs/foundry/aip-evals/overview).

Confidence: high for deterministic review/report features; AI quality requires actual evaluation through an approved model, not a marketing label.

### 7. Opt-in monitoring with useful changes and honest delivery state

Allow users to save scoped monitors on authorized case entities/sources, specify interval and expiration, and receive in-app change events/digests. Compare normalized meaningful fields while retaining raw snapshots. An unavailable provider means unknown freshness, not “no change”. Provider gates still apply to every scheduled run; email/Slack delivery needs separate authorized integration and verification.

Acceptance: an unchanged fixture emits no duplicate alert; a changed field produces one diff with before/after sources; a 429/403 creates a visible blocked/stale monitor rather than requerying repeatedly; disabling/expiring the monitor prevents future jobs. Backlog/restart does not duplicate notifications. The displayed next-run/status corresponds to actual scheduling. Cross-case and revoked-access events cannot leak data.

Evidence: Foundry documents schedules and user-bound Automate action permissions. OpenCTI documents object/source/event filters, change triggers and buffered digests; its docs also distinguish deletion from visibility loss. [Schedules](https://www.palantir.com/docs/foundry/data-integration/schedules), [Automate actions](https://www.palantir.com/docs/foundry/automate/effect-actions), [OpenCTI notifications](https://docs.opencti.io/latest/usage/notifications/).

Confidence: high for in-app monitoring; external notification delivery and paid refresh entitlement are separate postconditions.

### 8. Portable exports and documented integrations

Deliver versioned case JSON plus CSV/GEXF and a plain-language report first; add FtM mapping for people/companies/assets and STIX 2.1 for appropriate cyber observables/reports/relationships. Do not force all person/corporate facts into CTI semantics. Define per-target adapters that preserve sources, identifiers, dates, confidence and access markings, and report lossy fields.

Acceptance: export/import a synthetic case round-trips IDs, relationship direction, multiple source observations, missing values and review states; CSV formula cells are escaped and XML is encoded; access-restricted fields do not export. FtM/STIX files validate against their target model, with no claim that STIX alone preserves every app-specific review field. A Maltego transform can read one selected authorized case entity and emit typed related entities from fixture data; an OpenCTI adapter can serialize/import a fixture and resume an SSE cursor without duplicate events. Real vendor endpoints remain unverified until exercised with approved access.

Evidence: current Maltego SDK has typed graph/entity APIs; OpenCTI GraphQL enforces the token user's privileges and streams filter by rights; FtM's MIT model provides normalization and mappings independently of the sunset Aleph server. [Maltego SDK](https://github.com/MaltegoTech/maltego-transforms), [OpenCTI GraphQL](https://docs.opencti.io/latest/reference/api/), [OpenCTI streams](https://docs.opencti.io/latest/reference/streaming/), [FtM project](https://github.com/alephdata/followthemoney).

Confidence: high for standards files and fixture-validated adapters; medium for product interoperability until licensed-client testing.

## Build boundary for both apps

Keep the shared domain/import/export logic portable and independently testable in JavaScript/TypeScript. Use each app's existing server authentication and database authorization; do not replace the current provider pipeline, Supabase account route, PKCE flow, server key handling or browser-worker boundary. Make source adapters optional and capability-driven, with explicit configuration/entitlement/last-success metadata. Local fixture success is adapter validation; a live connector is only verified when an authorized request to the real product creates or retrieves the expected case record and preserves its permissions and source references.

The sequence with the fewest dependencies is: observation schema + deterministic imports, source/evidence inspection, graph/timeline, review and audit, portable exports, then opted-in monitoring and individual vendor adapters. This allows real useful features and file integrations to ship without misrepresenting a vendor purchase or unavailable product access.
